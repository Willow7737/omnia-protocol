# ADR-002: SettlementLayer Trait Requirements

> 🎯 Audience: Architects
> 🔗 Context: Part of the adr documentation section
> 📅 Last Updated: 2026-05-20

**Status**: Implemented
**Date**: 2026-05-14
**Updated**: 2026-05-16
**Decision**: Define an async `SettlementLayer` trait that abstracts L1 settlement operations, enabling multi-chain deployment without modifying the L2 state machine.

## Context

The Omnia Protocol operates as an L2 rollup that must periodically settle its state on an L1 blockchain. The L2 state machine — comprising the causal graph, consensus engine, shard router, and state root computation — is entirely chain-agnostic. It should never contain Ethereum-specific types, Bitcoin script logic, or Solana account model assumptions.

The settlement layer is the bridge between Omnia's L2 and the outside world. It handles four critical responsibilities:

1. **Data availability**: Posting batch data to L1 so that anyone can reconstruct L2 state.
2. **Proof verification**: Submitting and verifying zero-knowledge proofs that attest to the correctness of state transitions.
3. **Bridge operations**: Facilitating asset deposits (L1 → L2) and withdrawals (L2 → L1).
4. **Proof bundle settlement**: Submitting a complete `ProofBundle` for verification and state root commitment on L1.

The trait must be implemented separately for each L1 chain. Currently, four adapters exist in `zk/src/settlement/`:

- `ethereum.rs` — Full (simulated) implementation with a Solidity contract (`zk/contracts/ethereum/OmniaRollup.sol`)
- `bitcoin.rs` — Stub returning `SettlementError::NotImplemented`
- `solana.rs` — Stub returning `SettlementError::NotImplemented`
- `celestia.rs` — Stub returning `SettlementError::NotImplemented`

## Decision

We adopt the following trait definition (as implemented in `zk/src/settlement/mod.rs`):

```rust
#[async_trait]
pub trait SettlementLayer: Send + Sync {
    fn chain_id(&self) -> &'static str;

    async fn post_batch(&self, batch_data: &[u8]) -> Result<String, SettlementError>;

    async fn verify_proof(
        &self,
        old_root: &[u8; 32],
        new_root: &[u8; 32],
        proof: &[u8],
    ) -> Result<bool, SettlementError>;

    async fn latest_state_root(&self) -> Result<[u8; 32], SettlementError>;

    async fn deposit(&self, l2_did: &str, amount: u64) -> Result<String, SettlementError>;

    async fn request_withdrawal(
        &self,
        l2_did: &str,
        amount: u64,
    ) -> Result<String, SettlementError>;

    async fn submit_batch(&self, bundle: &ProofBundle) -> Result<String, SettlementError>;
}
```

### Why `async_trait`

All settlement operations involve L1 RPC calls, which are inherently I/O-bound:

- `post_batch()` submits a transaction to L1 and waits for inclusion, which can take seconds (Ethereum) to minutes (Bitcoin).
- `verify_proof()` may call a smart contract's verification function on L1.
- `latest_state_root()` queries an L1 RPC endpoint for the latest confirmed state root.
- `deposit()` and `request_withdrawal()` interact with bridge contracts on L1.
- `submit_batch()` submits a `ProofBundle` to L1 for verification and state root commitment.

Using `async_trait` allows the substrate runtime to yield the Tokio task while waiting for L1 responses, rather than blocking an OS thread. The `#[async_trait]` macro transforms the trait into one that returns `Pin<Box<dyn Future>>`, which is the standard pattern for async traits in Rust prior to native `async fn` in traits (stabilized in Rust 1.75, but with limitations that `async_trait` still addresses for object-safe traits).

### Method Contracts

**`chain_id()`** returns a static string identifying the L1 chain (e.g., `"ethereum"`, `"bitcoin"`). This is used for logging and routing, not for consensus logic.

**`post_batch(batch_data: &[u8])`** accepts raw batch data bytes and returns an L1-specific reference string (transaction hash, block height, etc.). The batch data format is defined by the ZK operator module (`zk/src/operator.rs`) and is independent of the settlement layer. In the Ethereum adapter, the batch data is hashed with BLAKE3 to produce a simulated transaction hash.

**`verify_proof(old_root, new_root, proof)`** takes the previous state root, the new state root, and the transition proof bytes. It returns `Result<bool, SettlementError>`, where `Ok(true)` means the proof was verified on L1. The `old_root` and `new_root` are `[u8; 32]` — matching the `CausalGraph::state_root()` return type. The proof bytes are opaque to the trait; they are generated by the ZK prover (`zk/src/prover.rs`). In the Ethereum adapter (Phase 0), this stub checks that the proof is non-empty and at least 32 bytes.

**`latest_state_root()`** queries L1 for the most recently confirmed state root. This enables L2 to detect if it has fallen behind L1 (e.g., after a network partition) and to verify that the L1 state root matches the L2 state root. In the Ethereum adapter, this returns `[0u8; 32]` (stub).

**`deposit(l2_did, amount)`** locks assets on L1 and credits them on L2. The `l2_did` parameter identifies the recipient on L2 using a DID string (e.g., `"did:omnia:alice"`). In the Ethereum adapter, this simulates a deposit by returning a formatted transaction hash.

**`request_withdrawal(l2_did, amount)`** initiates a withdrawal from L2 to L1. The actual withdrawal may require a proof and a challenge period before assets are released on L1. In the Ethereum adapter, this simulates a withdrawal request.

**`submit_batch(bundle: &ProofBundle)`** submits a complete `ProofBundle` (from `zk/src/proof_bundle.rs`) to L1 for verification and settlement. This is the preferred method for production use — it carries the structured proof bundle with version, state roots, transition proof, batch Merkle root, and L1 anchor. In the Ethereum adapter, the bundle is serialized with `postcard` and posted as simulated calldata.

### How New L1 Adapters Are Added

To add support for a new L1 chain, a developer:

1. Creates a new file in `zk/src/settlement/` (e.g., `avalanche.rs`).
2. Implements the `SettlementLayer` trait for a struct (e.g., `AvalancheAdapter`).
3. Adds the module and re-export in `zk/src/settlement/mod.rs`:
   ```rust
   pub mod avalanche;
   pub use avalanche::AvalancheAdapter;
   ```
4. Implements all seven async methods using the L1's RPC client or SDK.
5. Returns `SettlementError::NotImplemented` for any methods that cannot be supported on that chain.

No changes to the substrate, consensus, or shard logic are required. The L2 state machine remains completely L1-agnostic.

### Error Handling

`SettlementError` provides four variants that cover the failure modes of settlement operations:

- `RpcError(String)` — Network or RPC-level failure (timeout, connection refused, etc.)
- `ProofVerificationFailed(String)` — The L1 verifier rejected the proof
- `BridgeError(String)` — Deposit or withdrawal failed (insufficient L1 liquidity, invalid address, etc.)
- `NotImplemented(String)` — The operation is not yet implemented for this chain

This enum is defined alongside the trait in `zk/src/settlement/mod.rs` and is shared by all adapters.

### Ethereum Adapter Details

The `EthereumAdapter` (`zk/src/settlement/ethereum.rs`) is the only non-stub adapter. Key details:

- Constructor: `EthereumAdapter::new(rpc_url, contract_address, operator_key)`
- `chain_id()` returns `"ethereum"`
- All methods are simulated in Phase 0 (no real RPC calls)
- `post_batch()` and `submit_batch()` produce BLAKE3-based simulated transaction hashes
- `verify_proof()` checks `!proof.is_empty() && proof.len() >= 32`
- The adapter references the Solidity contract at `zk/contracts/ethereum/OmniaRollup.sol`

## Consequences

- **Positive**: The L2 state machine is completely L1-agnostic. Switching settlement layers requires zero changes to consensus, the causal graph, or shard logic.
- **Positive**: New L1 chains can be added by implementing the trait, with no risk of breaking existing functionality.
- **Positive**: `async_trait` allows non-blocking I/O, which is essential for maintaining the substrate's target throughput of 10,000 TPS.
- **Positive**: The `submit_batch()` method provides a clean interface for submitting structured `ProofBundle` data, enabling future L1 verifiers to parse and verify proofs without custom encoding.
- **Negative**: `async_trait` adds a small heap allocation per method call (boxing the future). This is negligible compared to the I/O latency of L1 RPC calls.
- **Negative**: The `batch_data: &[u8]` parameter is untyped — the settlement layer does not know the structure of the batch. This is intentional (chain-agnosticism) but means that each adapter must parse the batch data independently.
- **Trade-off**: The trait uses `String` for error messages rather than structured error codes. This mirrors the `EventProcessor` design: the caller (the ZK operator) logs the error but rarely acts on its specific content.
